# Maintain a verification skill

A feature map rots the moment the app changes. This skill is the upkeep loop for a skill generated by `/create-verification-skill`. Cover every feature file from source and exercise every feature live.

## Outcomes

Pick one and state it:

- **clean** — every feature got source and live coverage; nothing worth shipping. No branch, no PR.
- **changed** — one PR ships proven doc, harness, or map corrections.
- **blocked** — coverage could not finish or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

Only edit the verification skill's own directory (SKILL.md, features/, scripts). Never edit product code during a run. A behavior the map describes that the app no longer does is either doc drift (fix the map) or a product regression (report it, don't paper over it).

## Pass

### 0. Locate the target

Find the verification skill to maintain: `.cursor/skills/verify-*/`. Multiple candidates → ask which one. None → stop and point at `/create-verification-skill`.

### 1. Index hygiene

Read the feature map README and glob its sibling files. Fix missing, extra, duplicate, or dead entries.

### 2. Source wave

One read-only subagent per feature file, launched concurrently. Each explains "how does this user-facing feature work?" from source, flags likely doc drift with citations, and returns one concise live-verification recipe.

Return shape per feature:
- Feature summary
- Source entry points (files, components, routes)
- Likely drift or none
- One recipe for live verification

Children never drive the app and never edit files.

### 3. Reconcile

Every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift. Sweep recent churn for user-facing surfaces missing from the map.

### 4. Live pass

Required even when source looks clean. Follow the verification skill's launch model.

**Invariants to hold the whole pass:**

1. **Doctor before drive** — health-check the dev server before first drive, and after any failed drive. If doctor can't see the failure (wedged UI state on healthy process), reset or relaunch.

2. **Evidence survives cleanup** — check evidence exists at named location after each cleanup, don't assume.

3. **Nothing outlives its usefulness** — failed-iteration residue is cleaned, whether session is stuck, exited, or shared.

**For each feature:**
1. Navigate to the feature via user path
2. Exercise the documented interactions
3. Verify observable end state
4. Capture evidence (screenshot + any side effects)
5. Compare against feature file expectations
6. Log drift findings

A doctor failure caused by skill drift is drift: fix it under edit scope and retry once before calling the pass blocked.

### 5. Triage

| Finding | Action |
|---------|--------|
| Wrong/missing user-POV description | Doc drift → fix the map |
| Working behavior harness can't drive | Harness gap → fix the harness |
| App behavior actually broken | Product gap → report for user, keep out of PR |
| Selector changed | Update feature file selector |
| New feature not mapped | Add feature file |

### 6. Ship or stop

**For changed:** One PR of proven corrections. Re-read every changed file first.

**For clean or blocked:** No PR. Report the outcome and coverage honestly.

## Run notes

Keep concise notes in a scratch location:
- Features covered
- Unreachable prerequisites
- Confirmed drift
- Outcome

Don't commit these notes.

## Frontend-specific checks

### Component drift
```bash
# Find components referenced in feature map
grep -r "data-testid" src/ | grep -v node_modules

# Compare against feature files
ls .cursor/skills/verify-*/features/
```

### Route changes
```bash
# Check routes against feature paths
grep -r "path:" src/routes/ || grep -r "Route" src/
```

### Selector validity
```javascript
// Before driving, verify selector exists
const exists = await page.locator('[data-testid="feature"]').count();
if (exists === 0) {
  console.log('DRIFT: selector not found');
}
```

## Integration with fstack

This skill is called:
- On a schedule (weekly, sprint boundary)
- After significant feature changes
- Before releases
- When verification starts failing unexpectedly
